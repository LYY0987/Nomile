# AI 自然语言重命名 · 方案 v2

> 状态：设计稿，未实现。相较 v1 的两处根本改动：**AI 有自己的母模板（槽位结构），不受现有 15 条规则限制**；**AI 是独立的左侧面板，可与规则栈自由切换**。

## 0. 与 v1 的差别

| | v1（已废弃） | v2 |
|---|---|---|
| AI 产出 | 只能映射到现有 15 条规则 | 产出自己的**命名方案**（槽位序列 + 布局 + 收尾），组合自由度不受规则数量限制 |
| 母模板 | 无 | AI 有一套受控槽位语法，从描述里抽取参数填进去 |
| 入口 | 规则区里加一行输入 | 左侧独立面板，`规则栈 / AI 命名` 双模式切换 |

不变的底线：AI 只产出**受控结构**，不产出最终文件名清单，不碰执行；一切仍经 `build_plan` 预览，用户点执行才改名。

## 1. 母模板是什么

一条命名方案 = **有序槽位（slot）序列 + 连接符 + 收尾处理**。槽位是有限枚举，AI 决定"用哪些、什么顺序、什么参数"，但每个槽位都是确定性的、可在 Rust 里求值的积木。

```json
{
  "segments": [
    { "type": "text",  "value": "IMG_" },
    { "type": "date",  "source": "shot",   "format": "yyyyMMdd" },
    { "type": "text",  "value": "_" },
    { "type": "orig",  "part": "stem" },
    { "type": "seq",   "start": 1, "step": 1, "pad": 3 }
  ],
  "join": "",
  "keepExt": true,
  "case": "keep",
  "trim": true
}
```

**槽位清单（v1 实现范围）**

| type | 含义 | 参数 |
|---|---|---|
| `text` | 固定文本 | `value`（≤64 字） |
| `orig` | 原名的一部分 | `part`: `stem` / `full` / `ext`；可选 `slice: [start, end]` |
| `date` | 时间 | `source`: `modified` / `created` / `shot`(EXIF) / `now`；`format`（校验可解析） |
| `seq` | 序号 | `start` `step` `pad`（1–6 位） |
| `total` | 总数 | 无 |
| `index` | 当前序号（同 seq 但只取值） | `pad` |
| `meta` | 媒体元数据 | `key`: 相机/机型/镜头/宽/高/时长/标题/作者/专辑/曲目 |
| `folder` | 所在文件夹名 | 无 |
| `rand` | 随机串 | `len`（4–8） |
| `replace` | 对**前一段输出**做查找替换 | `find` `replaceWith` `regex` |
| `case` | 对**前一段输出**改大小写 | `mode` |
| `clean` | 收尾清理 | `spaces` `illegal` `collapse` `stripCopyMarks` |

这套槽位能做出来的东西，比 15 条规则的单条更强（例：`日期_相机_序号_原名`），也比"任意字符串拼接"更安全（没有表达式、没有注入面）。

**母模板库**（内置 8 套，供 AI 参考、也供用户直接套用）：
`前缀_原名`、`原名_日期`、`日期_序号`、`相机_序号`、`前缀_日期_序号`、`序号_原名`、`原名_序号_后缀`、`清理后原名`。

## 2. AI 怎么用母模板

三步，都发生在 Rust 侧：

1. **抽取**：把描述 + 文件名样本（≤30 个，只含文件名）+ 母模板清单发给模型，要求返回 `{plan, explanation, confidence, fields}`。
2. **校验**：槽位类型白名单、文本长度、日期格式可解析、`pad` 范围、段数 ≤ 12、`seq` 至多一个、`orig` 至多两个。不合法 → 把错误回灌重试一次，仍失败就提示换说法（不猜）。
3. **求值**：用户在右侧预览表里看到的就是 `compose(plan, entry, index, total, meta)` 的确定性结果。

`fields` 是给界面的"关键信息表"用的，例如 `{前缀:"IMG_", 日期格式:"yyyyMMdd", 序号位宽:3}`，让用户一眼看到 AI 抽到了什么，并可手改。

**多轮增量**：把上一版 `plan` 一起发，只改动相关段——"序号改成 4 位"只改 `seq.pad`，其他段原样返回。

## 3. 怎么接进现有架构

新增一条规则变体（第 16 条）：

```rust
Rule::Compose { plan: NamePlan }
```

- `apply_stack` 里新增一个分支，调用纯函数 `domain/compose.rs::compose(plan, ctx, index, total)`。
- 因为它是规则，AI 方案天然进入现有规则栈：`build_plan` → 预览 → 两阶段执行 → 撤销，**全部零改动**。
- 也可以和手动规则混用：AI 生成一条 `Compose`，后面再接「清理」「改扩展名」等，链式生效。
- 界面上这条规则显示为「AI 命名方案」卡（可展开看分段，可编辑字段，可删）。

代价：`RuleKind` 从 15 项变 16 项，`types.ts`、`createRule`、`ruleCatalog`、`RulePanel` 各加一处；`model.rs` 加变体与默认值。

## 4. 界面：左侧双模式

```
┌─────────────────────────┐
│ [ 规则栈 ] [ AI 命名 ]  │  ← 左侧栏顶部，分段切换
├─────────────────────────┤
│  （切换后整块替换）     │
└─────────────────────────┘
```

**规则栈模式**：现在的 `RulePanel`（常用规则、预设、规则库）原样保留。

**AI 命名模式**：

```
┌───────────────────────────────┐
│ 用一句话描述                  │
│ ┌───────────────────────────┐ │
│ │把照片按拍摄日期重命名，     │ │
│ │序号 3 位                   │ │
│ └───────────────────────────┘ │
│ [ ✨ 生成 ]                   │
│                               │
│ 母模板  ●──●──●  （分段 chips）│
│   IMG_ │ 拍摄日期 │ _ │ 原名 │ 序号3
│                               │
│ 关键信息                      │
│   前缀 [IMG_            ]     │
│   日期 [拍摄时间 ▾] [yyyyMMdd]│
│   序号 [起始1] [步长1] [3位]  │
│   分隔符 [_     ]  大小写 [不变]│
│                               │
│ 试算：IMG_20230506_IMG_001_001 │
│       IMG_20230507_IMG_002_002 │
│                               │
│ [应用为规则] [重新生成] [存预设]│
└───────────────────────────────┘
```

- 两个模式各自保留自己的编辑状态，来回切换不丢；
- 右侧列表与预览表**共用同一个会话**，切换后立刻按当前生效的规则栈重算；
- 「应用为规则」= 往规则栈插入/替换一条 `Compose`，切回规则栈模式能看到它，可继续在其后加手动规则；
- 「重新生成」会带上当前 `plan` 做增量；
- 没有 Key 时：区域不隐藏，只是「生成」改为本地解析（母模板库 + 关键词填参数），或直接手动选母模板改参数。

## 5. 校验与安全

| 项 | 规则 |
|---|---|
| 槽位类型 | 必须在白名单内，未知 type 直接拒 |
| 段数 | ≤ 12；`seq` 至多 1 个；`orig` 至多 2 段 |
| 文本 | `text.value` ≤ 64；整体渲染结果交给现有「路径超长/非法字符」校验兜底 |
| 日期格式 | 必须是 chrono 可解析的格式串（先试算一次） |
| 正则 | 仅 `replace` 槽位可用，先编译校验 |
| 空名/全空 | 渲染为空 → 交给现有 `EmptyName` 校验报错，不静默 |

模型永远拿不到"执行"能力；它输出的结构里没有任何字段能表达"删除/移动/改写扩展名之外的动作"。

## 6. 测试

- **槽位求值**：每个槽位单测 + 组合单测（含中文、空 meta、负数切片）
- **AI 方案校验**：非法 type / 超长 / 坏格式 / 多 seq / 超段数 → 全部被拒
- **快照**：30 条中文描述 → 期望 plan JSON（离线固定响应）
- **端到端**：plan → Rule::Compose → build_plan → 断言预览名
- **契约**：前端 `types.ts` 的 `NamePlan` 与 Rust 同构（序列化往返）
- **界面**：切换模式不丢状态、应用后规则栈出现 Compose 卡

## 7. 里程碑

| 阶段 | 内容 |
|---|---|
| M1 | `NamePlan` 结构 + `Rule::Compose` + `compose()` 求值 + 单测（无 UI 可验证） |
| M2 | AI 客户端 + Prompt（含母模板库 few-shot）+ 校验/修复回路 + Key 存储 |
| M3 | 左侧双模式切换 + AI 面板（描述、模板 chips、字段表、试算、应用/重生成/存预设） |
| M4 | 增量多轮、无 Key 时的本地解析、错误文案、预设复用 |
