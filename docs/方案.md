## 1. 需求理解

### 1.1 产品定位

一个 Windows 桌面端的**通用批量文件/文件夹重命名器**，对标 PowerToys PowerRename、Advanced Renamer、Bulk Rename Utility。

三条铁律，它们决定了整个架构：

1. **预览即真相**：用户看到的"原名 → 新名"表格，必须和真正执行时发生的事逐字一致。
2. **执行可撤销**：任何一次批量操作，都能一键回滚到操作前，包括关掉程序再打开之后。
3. **规则可复用**：一套规则能保存为预设，下次对另一个目录直接套用。

### 1.2 功能边界

**P0（首版必须有）**

| 场景 | 说明 |
|---|---|
| A. 统一改名 | 加前缀/后缀、删固定字符、替换文本、改大小写 |
| B. 批量编号 | 001、002…… 起始值/步长/位数/编号位置可配 |
| C. 正则重构 | 用正则 + 捕获组把 `IMG_20230101_123456.jpg` 变成 `2023-01-01_123456.jpg` |
| D. 模板合成 | `${name}_${n:3}.${ext}` 这种模板串，是最灵活的一层，覆盖 A~C 的大部分组合 |
| E. 安全护栏 | 预览、冲突检测、非法名检测、执行前后校验、撤销 |

**P1（第二版）**

- 多规则串联（规则栈，可拖拽排序、单条启停）—— 实际上首版就要做成栈结构，只是规则种类先做 5~6 个
- 排序依据：文件名 / 修改时间 / 创建时间 / 大小 / 随机 / 手动拖拽
- 预设管理与导入导出
- 历史记录列表（最近 N 次操作 + 逐条撤销）

**P2（后续）**

- EXIF 拍摄时间命名、音频/视频元数据命名
- 规则冲突可视化、批量规则试算对比
- CLI 模式（复用同一套 Rust 规则引擎）

**明确不做**

- 跨目录移动、复制、删除（只改名，不做搬运，避免数据风险）
- 文件内容编辑、去重、格式转换
- 云同步 / 多端

### 1.3 关键非功能指标

| 指标 | 目标 |
|---|---|
| 预览速度 | 1 万文件、3 条规则，Rust 侧计算 < 300ms |
| 承载规模 | 10 万文件列表可加载、表格不卡（虚拟滚动） |
| 执行速度 | 1 万文件 rename < 3s（NTFS 同目录 rename 本身是元数据操作） |
| 撤销可靠性 | 程序崩溃后重启仍能撤销（预写日志） |
| 编码安全 | 中文 / emoji / 全角字符 / 混合 Unicode 全程无损，禁止 `to_string_lossy` 参与写盘 |
| 误伤底线 | 目标文件已存在时，**默认禁止覆盖**，需显式选择策略 |

### 1.4 我做的假设（如不成立请纠正）

- 只交付 **Windows x64 桌面版**（Tauri 天然跨平台，但不做 mac/Linux 的适配与验证）
- 单机单用户，配置存本地，不需要账号体系
- 首版不做 CLI
- 只处理**同一目录内**的重命名，不跨盘/跨目录

## 3. 技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 应用框架 | **Tauri 2.x** | 复用系统 WebView2，安装包约 5~10 MB（Electron 是 100 MB+），内存占用低；Rust 后端直接做文件系统操作，比 Node 的异步 IO 更可控 |
| 前端框架 | **React 19 + TypeScript + Vite** | 表格与虚拟滚动生态最成熟（TanStack Table + TanStack Virtual），规则栈的拖拽排序有 dnd-kit 可用；TS 保证与 Rust 类型的编译期一致性 |
| 状态管理 | **Zustand** | 轻量，不需要 Redux 那套样板代码 |
| 样式 | **Tailwind CSS v4 + 自建组件** | 桌面工具界面偏密集紧凑，Tailwind 迭代快；不引大而全的 UI 库，避免体积和风格失控 |
| 规则引擎位置 | **Rust（唯一真相）** | 前端只负责编辑规则、渲染结果。计算、校验、执行全在 Rust，保证"预览"和"执行"用同一份代码，不会出现预览对、执行错 |
| 类型同步 | **ts-rs** | 从 Rust 结构体自动生成 `src/lib/bindings.ts`，杜绝前后端字段漂移 |

**核心 crate**

| crate | 用途 |
|---|---|
| `tauri` / `tauri-build` | 应用框架与构建 |
| `serde` / `serde_json` | 规则与计划序列化 |
| `regex` | 正则规则（Rust 的 regex 是线性时间、无回溯灾难，比 JS RegExp 安全） |
| `chrono` | 日期格式化、时间戳命名 |
| `walkdir` | 目录扫描（可控深度、跳过符号链接） |
| `thiserror` / `anyhow` | 领域错误 vs 兜底错误的分离 |
| `uuid` | 操作 ID（撤销日志文件名） |
| `dirs` | 定位 app data 目录（`%APPDATA%\Nomile`） |
| `rayon` | 大批量文件元数据并行读取 |
| `unicode-normalization` | 文件名 NFC 归一化，处理 macOS 拷贝过来的 NFD 名字 |
| `tracing` + `tracing-subscriber` | 结构化日志，写到本地文件便于排障 |
| `ts-rs` | 生成前端类型 |

P2 阶段再引入 `kamadak-exif`（照片）、`lofty`（音视频元数据）、`trash`（安全移入回收站）。

## 4. 架构设计

### 4.1 分层

```
┌─────────────────────────────────────────────────────────┐
│  React 前端                                               │
│  来源面板 │ 规则栈 │ 预览表 │ 历史 │ 设置                  │
└───────────────────────┬─────────────────────────────────┘
                        │ invoke(command, payload) / event(progress)
┌───────────────────────▼─────────────────────────────────┐
│  Commands 层（薄）  src-tauri/src/commands/*.rs          │
│  scan_dir / preview / execute / undo / list_history ...  │
└───────────────────────┬─────────────────────────────────┘
┌───────────────────────▼─────────────────────────────────┐
│  Domain 层（纯逻辑，无 IO，可单测）                        │
│  rules（规则实现） → planner（算新名） → validator（校验）│
└───────────────────────┬─────────────────────────────────┘
┌───────────────────────▼─────────────────────────────────┐
│  Infra 层  fs_ops / history_store / config_store         │
└─────────────────────────────────────────────────────────┘
```

这条分层的关键收益：**Domain 层是纯函数**，输入 `(文件列表, 规则栈)` 输出 `(计划, 校验结果)`，不碰磁盘。所以规则的正确性可以用 `cargo test` 全量覆盖，不需要手工点界面验证。

### 4.2 核心数据模型

```rust
// 扫描出来的一个条目
struct FileEntry {
    id: u64,
    path: PathBuf,
    parent: PathBuf,
    name: String,        // 不含扩展名
    ext: String,         // 不含点，可为空
    size: u64,
    mtime: i64,
    is_dir: bool,
    readonly: bool,
}

// 规则（serde tagged enum，前端直接传 JSON 过来）
enum Rule {
    Replace   { find: String, replace_with: String, case_sensitive: bool, use_regex: bool },
    Sequence  { start: u64, step: u64, pad: u8, position: SeqPos, separator: String },
    Template  { pattern: String },
    Case      { mode: CaseMode },        // upper/lower/title/sentence
    Insert    { text: String, at: InPos },   // 前缀/后缀/指定偏移
    Remove    { .. },                    // 删指定区间/删指定字符集
    Cleanup   { .. },                    // 非法字符、空格转下划线、压缩重复字符
}

struct RuleStack {
    rules: Vec<RuleInstance>,   // 每项含 enabled、target(Name/Ext/Both)
}

// 计划条目
struct PlanItem {
    entry_id: u64,
    src: PathBuf,
    dst: PathBuf,
    changed: bool,
    issues: Vec<Issue>,   // Error 阻断 / Warning 提示
}

enum IssueKind {
    IllegalChar, ReservedName, EmptyName, TooLong,
    DuplicateInBatch, AlreadyExists, CaseOnlyChange, SameName,
}
```

### 4.3 规则引擎语义

**流水线串联**：规则按栈顺序依次作用于"当前名字"，前一条的输出是后一条的输入。每条规则只作用于「文件名」或「扩展名」其中之一（`Target::Name | Extension`），要两边都改就放两条规则。`Template` 是例外：它作用于完整文件名，扩展名得自己写 `${ext}`。

**模板变量表**（以 `domain/rules.rs::eval_token` 的实现为准）

| 变量 | 含义 |
|---|---|
| `${name}` / `${orig}` / `${full}` | 当前 stem / 最初 stem / 原始全名 |
| `${ext}` | 当前扩展名 |
| `${n}` `${n:3}` `${i}` `${index}` | 序号（值 = index + 1），可补零 |
| `${total}` | 本次处理总数 |
| `${date}` `${mtime}` `${ctime}` | 修改 / 创建时间，默认 `yyyy-MM-dd`，可带格式 |
| `${size}` | 字节数 |
| `${parent}` | 父目录名 |
| `${rand}` `${rand:6}` | 以条目 id 为种子的确定性随机串（预览与执行必然一致） |
| `$$` | 转义成 `$` |

**元数据变量**（要读文件头才有，缺失留空并由校验器提示）

| 变量 | 含义 |
|---|---|
| `${shot}` `${shot:yyyyMMdd_HHmmss}` | EXIF 拍摄时间（DateTimeOriginal），默认精确到秒 |
| `${camera}` | 厂商 + 型号（型号本身已含厂商名时不重复写） |
| `${make}` `${model}` `${lens}` | 相机厂商 / 型号 / 镜头 |
| `${title}` `${artist}` `${album}` | 音视频标签 |
| `${track}` `${track:3}` | 曲目号，默认补零 2 位 |
| `${duration}` `${duration:mmss}` | 时长，整秒或 `02m35s` |
| `${width}` `${height}` | 像素尺寸 |

元数据是**按需读取**的：只有启用中的规则真的用了上面这些变量，才会打开文件读头。读过的按条目 id 进 session 缓存，一次会话内不重复读盘；读文件头是纯 IO，分 4~8 线程并行。第一次读 1 万个文件约数秒，之后预览是纯内存计算。

模板是"一层就能顶好几条规则"的设计，产品上放首位引导用户用模板，原子规则则是给不想学模板的人留的快捷入口。

### 4.4 校验器（决定"执行"按钮亮不亮）

校验顺序与分级：

| 级别 | 检查项 | 行为 |
|---|---|---|
| Error | 空文件名、含 `\ / : * ? " < > \|`、Windows 保留名（CON/PRN/AUX/NUL/COM1…）、路径超 260 字符 | 阻断执行，条目红色标注 |
| Error | 同批次内目标名重复 | 阻断，成组标出重复项 |
| Warning | 目标在磁盘上已存在 | 允许继续，但需用户选择冲突策略 |
| Info | 仅大小写变更（`file.txt` → `File.txt`） | 提示走两步 rename |

冲突策略两种：`自动加后缀 (1)(2)…` / `跳过该文件`。**默认是"自动加后缀"**，两种都不是覆盖——本工具任何情况下都不会覆盖已有文件。

### 4.5 执行器（事务化 + 可恢复）

rename 在 NTFS 同目录下是原子元数据操作，但一批 1 万个操作整体不原子。所以用**预写日志（WAL）+ 快照**：

```
%APPDATA%\com.nomile.app\operations\
├── 20261110-1530-a1b2c3\
│   ├── manifest.json     # 操作元信息：规则快照、文件数、开始时间、状态
│   └── journal.jsonl     # 逐行追加：Stage1{src,tmp,size,mtime} / Stage2{tmp,dst,...} / Fail
```

执行流程：

1. 建目录、写 `manifest.json`（含规则栈快照，便于日后"用同样规则再来一次"）
2. 逐条 rename，成功一条 → `journal.jsonl` 追加、flush
3. 单条失败（文件被占用 `ERROR_SHARING_VIOLATION`、权限不足）→ 按用户选择"跳过继续"或"立即中止"，写入失败原因
4. 结束写 `state.json`
5. 前端通过 `emit("rename:progress", {done, total, failed})` 拿到实时进度

之所以**不做并发**：rename 极快，1 万文件也就一两秒，而并发会让"目标是否已存在"的判定在多线程之间互相干扰，正确性收益远小于速度收益。只有元数据扫描（`stat`）那步用 rayon 并行。

**Windows 大小写专用处理**：`a.txt` → `A.txt` 在同目录下 `rename` 会返回"文件已存在"错误。处理办法是先 `a.txt` → `~tmpXXXX` → `A.txt`，两步走，日志里两条都记。

### 4.6 撤销

- 从最新一条 `completed | partial` 的操作开始，反序重放 journal：`to` → `from`
- 撤销前逐条校验：`to` 是否还存在、`size + mtime` 是否和记录一致。不一致 → 标记"文件已被外部改动，跳过"，不强行回推（防止把用户新写的内容搞错位）
- 撤销本身也写一条日志，`state.json` 记为 `rolled_back`
- 历史面板最多保留最近 50 条操作，超出按时间清理（可配）

### 4.7 前端关键点

- **预览表虚拟滚动**：`@tanstack/react-virtual` 只渲染可视行，10 万行不卡
- **差异高亮**：Rust 侧返回 `dst` 同时返回"变更片段区间"（diff spans），前端按区间上色，而不是在前端重新算 diff
- **规则栈拖拽**：`dnd-kit` 排序，改顺序即触发重新预览（debounce 250ms）
- **长任务不阻塞**：`execute` 是 async command，前端保持可交互，用进度条 + 取消按钮（取消 = 中止后续条目，已做的保留并可撤销）

## 6. 界面结构（三栏 + 底栏）

```
┌──────────────────────────────────────────────────────────────┐
│ [目录路径 ▾] [扫描]   过滤 glob:[含] [排除]        预设 ▾ ⚙  │
├──────────────┬────────────────────────┬──────────────────────┤
│ 来源         │ 规则栈                 │ 预览                 │
│ ┌──────────┐ │ ① 前缀 "2023_"   ⣿  │ 原文件名 → 新文件名  │
│ │ ▸ 子目录 │ │ ② 模板 ${orig}_${n:3} │ 红色=冲突 蓝色=变更  │
│ │ ▸ 文件…  │ │ ③ 扩展名小写          │ 全选/反选 排序         │
│ └──────────┘ │ [+ 添加规则]           │ …（虚拟滚动）         │
│  排序: 名称  │                        │                      │
├──────────────┴────────────────────────┴──────────────────────┤
│ 共 1,234 项 · 将变更 1,180 · 冲突 4        [撤销上次] [执行] │
└──────────────────────────────────────────────────────────────┘
```

交互约定：改任何规则 → 250ms 防抖后自动重新计算预览（不需要点"预览"按钮）。"执行"按钮有 Error 时置灰，hover 给出原因。

## 8. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 文件被进程占用 | `rename` 返回 ERROR_SHARING_VIOLATION | 记录失败原因，跳过该条继续，结束后列出失败清单并提供"重试" |
| 大小写变更 | `a.txt→A.txt` 报"目标已存在" | 临时名两步 rename |
| 目标已存在导致覆盖 | 数据丢失 | 默认拒绝覆盖；三种显式策略，覆盖必须用户手选 |
| 路径超长（>260） | Windows 后端 API 报错 | 校验阶段前置拦截并明确提示；不静默截断 |
| 中文/emoji 文件名 | 乱码、改名后变 `?` | 全程 `PathBuf` + `OsStr`，只有展示层用 `to_string_lossy`；NFC 归一化后再比较 |
| 目录里既有文件与规则冲突 | 一执行就炸 | 预览阶段的 validator 已全量算出，执行前二次确认（磁盘状态可能变了） |
| 长任务阻塞 UI | 界面假死 | 全 async command + 进度事件 + 取消令牌 |
| 撤销时文件已被外部改动 | 回推错位 | 撤销前比对 `size + mtime`，不匹配则跳过并告知 |
| C 盘空间（35GB） | target 膨胀 | `.cargo/config.toml` 设 `target-dir = "F:\\MyProject\\Nomile\\target"` |
| 规则语义前后端不一致 | 预览对、执行错 | 规则引擎只在 Rust 存在；前端零计算逻辑（除渲染） |
